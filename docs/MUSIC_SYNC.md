# 音乐同步器

脚本从本地 audio/ 扫描专辑，使用 R2 S3 API 增量上传媒体，再发布 Catalog。它不构建网站。所有命令使用 .env.local 中的凭证；执行前确认 Bucket 与本地曲库目标一致。

## 命令

~~~powershell
pnpm.cmd music:sync
pnpm.cmd music:watch
pnpm.cmd music:prune
~~~

| 命令 | 行为 |
| --- | --- |
| music:sync | 扫描当前曲库，增量上传，发布 Catalog，并按规则清理失去引用的已管理对象 |
| music:watch | 递归监听 audio/，变化稳定后串行执行 music:sync |
| music:prune | 只读扫描 sync-state 记录的疑似过期对象，发送 HeadObject 并打印预览；不发布 Catalog，不删除任何对象 |

music:prune 依然需要本地音频、有效 sync-state 和可读凭证。它不是清理命令。真正删除动作只会发生在 music:sync。

## 增量判断与发布顺序

同步器只管理 albums/<安全 ID>/ 下的受控音频、LRC 和封面/展示/曲目图片路径：

1. 扫描整个 audio/，生成本次候选 Catalog 和对象清单。
2. 根据文件来源、大小、修改时间和 SHA-256 状态识别新增、变更和未变化对象。
3. 未变化内容跳过；新增或内容变化的媒体上传到 R2。
4. 每个上传对象随后执行 HeadObject，检查对象存在且远端 ContentLength 等于本地大小。
5. 若源文件在规划或上传期间发生变化，中止本轮，避免发布混合状态。
6. 生成带内容摘要修订参数的 Catalog，并在所有媒体验证后发布 catalog.json。
7. Catalog 成功后，才检查已经不再引用的历史受管对象并按安全规则决定是否删除。

Hash 用于本地增量决策和 URL 版本；HeadObject 校验实际确认对象存在和大小一致，不会回读整个对象逐字节比对。

## 安全清理条件

同步器只考虑以前由本同步状态登记、符合 albums/ 受控键模式且当前 Catalog 不再引用的对象。它不会对整个 Bucket 做通配清理，也不能清理从未登记过的对象。

只有同时满足以下条件才会自动删除：没有整张专辑被移除、扫描没有警告、待删对象不超过 3 个、待删数不超过状态文件已管理媒体对象的 5%。任何一项不满足就要求本轮人工确认。

交互式终端会列出对象、大小和原因，必须准确输入该轮显示的 DELETE <confirmation-token>。输入其他内容等同拒绝。非交互执行不会删除，已发布的新 Catalog 保持生效，对象和待删状态留待之后处理。扫描失败、audio/ 缺失、没有扫描到专辑、状态损坏或目标 Bucket 不一致时会直接拒绝同步/清理。

若存在清理对象，扫描警告会取消自动删除并要求人工确认；扫描为空或扫描程序失败则不会上传、发布 Catalog 或清理。若媒体上传或 HeadObject 验证失败，不会发布 Catalog，也不会进入删除阶段。Catalog 发布失败后同样不会删除旧对象。

删除前同步器会再次 HeadObject 并核对历史大小。若对象大小改变、仍被当前 Catalog 引用、键不符合受管模式或有任何引用检查失败，清理停止。

## 状态文件

本机 .music-cache/sync-state.json 记录目标 Endpoint/Bucket、受管媒体源路径、大小、修改时间、哈希、Catalog 哈希和待删除键。它是安全判断远端所有权与增量上传的重要历史，不含 API Secret。

- 应备份状态文件，但不要提交到 Git。
- 换电脑时先安全迁移本地 audio/ 与对应目标的状态文件，并保留文件结构。
- 重装后若状态丢失，不要直接对已有大型 Bucket 运行同步：没有历史时当前媒体会被视为首次上传，可能重新上传全部曲库；未登记的旧对象也无法由自动清理识别。
- 优先从原机器或备份恢复匹配该 Endpoint/Bucket 的状态。状态目标不同或格式损坏时脚本停止，不要手工修改 JSON 来绕过检查。
- 若无法恢复状态，先备份 Bucket 并选择经过人工规划的新 Bucket/迁移流程，再确认完整上传成本；不要伪造历史状态。

改 album.json 中的 id 会改变专辑对象前缀，导致当前媒体被识别为新对象、旧前缀进入待清理。长期维护时保持 ID 不变。

## 文件监听

music:watch 启动后监听 audio/ 的递归变化；事件间隔合并约 1 秒。随后它每秒比较音频树快照，等大小、修改时间和创建时间等记录连续 5 个间隔稳定后才同步，通常至少等待约 5 秒。变化继续发生时稳定计时重置。

同步执行期间的新事件会排队，前一轮结束后再运行；按 Ctrl+C 会停止监听、取消等待中的稳定检查，并等当前安全同步完成。脚本没有跨进程锁，请不要同时运行多个 watch、sync 或 prune 流程；本地终端只保留一个同步实例。

## 常见操作结果

| 操作 | 预期结果 |
| --- | --- |
| 新增专辑 | 新专辑及其媒体上传；校验后 Catalog 增加专辑；正常情况下所有动态展示区域随 Catalog 更新 |
| 新增歌曲 | 新曲目音频及匹配到的歌词/图片上传；Catalog 在媒体校验后更新播放列表 |
| 修改 LRC | 对应 LRC 对象按哈希判定变化并更新；Catalog 引用新版修订地址 |
| 替换封面 | cover 对象变化后重新上传，Catalog 指向含新摘要的 URL；不重新构建 Pages |
| 删除一首曲目 | Catalog 先删除引用，旧媒体随后进入清理计划。若其音频、歌词、图片总对象数不超过 3 且不超过管理总量 5%，没有专辑删除且没有扫描警告，可在 Catalog 发布后自动删；否则必须输入确认码 |
| 删除整张专辑 | Catalog 先移除该专辑；整张专辑删除永远要求本轮人工确认。拒绝或无 TTY 时旧对象保留并列为待清理 |
| 更改文件名 | 若派生的 ID/扩展名导致对象键变化，会新增对象并让旧键变成待清理；同内容同 ID 可能只更新本地状态而跳过重新上传 |
| 中断后恢复 | 修复网络/本地文件问题后再运行 music:sync。已记录成功的对象会跳过；未完成对象重试；部分删除的待处理历史保留并重新检查 |

任何删除示例都适用于用户主动在本地移除媒体后。不要为了测试同步器在真实 Bucket 上删除已有资源；测试应使用内置 MockUploader。
